## Armazenamento de mídia — `STORAGE_BACKEND` (Manutenção #71)

Desde a Manutenção #71, todo `FileField`/`ImageField` do projeto (comprovantes,
documentos administrativos, extratos de conciliação e qualquer campo futuro —
ex.: foto de perfil) é persistido e configurável por variável de ambiente, sem
precisar tocar em código/`settings.py` de novo.

```
STORAGE_BACKEND=local   (padrão, sem precisar setar nada) → grava no volume
                         Docker nomeado media_volume (projeto compose
                         resolvido: nome real confirmado via
                         `docker compose config` → uidcore_media_volume),
                         montado em /app/media no backend (rw) e /media
                         no nginx (ro). Sobrevive à recriação do container
                         a cada deploy (volume nomeado não é recriado por
                         `docker compose up`, só os containers).

STORAGE_BACKEND=s3      → qualquer serviço compatível com a API S3
                         (Cloudflare R2, Backblaze B2, Wasabi, AWS S3 real)
                         via django-storages. Bucket tratado como PRIVADO
                         por padrão (AWS_QUERYSTRING_AUTH=True) — a API
                         sempre devolve URL assinada (pre-signed, expira
                         em AWS_QUERYSTRING_EXPIRE segundos, default 3600),
                         nunca uma URL pública direta do bucket.
```

Variáveis exigidas quando `STORAGE_BACKEND=s3` (só nesse caso — em `local`
nenhuma delas é lida): `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`,
`AWS_STORAGE_BUCKET_NAME`, `AWS_S3_ENDPOINT_URL`, `AWS_S3_REGION_NAME`
(default `auto`), `AWS_MEDIA_PREFIX` (default `uidcore/media` — prefixo
dentro do bucket, útil se o mesmo bucket for compartilhado entre
projetos da fábrica).

**Procedimento operacional — migração local→bucket (RN-01):** a ser
executado quando o disco da VPS apertar (ela é compartilhada por
SystemD, ContratID, UidCore, LifeStyle e futuros forks). Copia o
conteúdo real do volume Docker local pro bucket S3-compatível já
configurado, sem perder nenhum arquivo:

```bash
# 1. Confirmar o nome exato do volume em uso (pode variar por nome do
#    projeto compose resolvido na VPS)
docker volume ls | grep media_volume

# 2. Instalar o rclone (ou usar `aws s3 sync` se o provedor for S3 puro)
#    dentro de um container efêmero com o volume montado, apontando pro
#    bucket já configurado via STORAGE_BACKEND=s3 (.env.prod)
docker run --rm \
  -v uidcore_media_volume:/source:ro \
  -e RCLONE_CONFIG_DEST_TYPE=s3 \
  -e RCLONE_CONFIG_DEST_PROVIDER=Other \
  -e RCLONE_CONFIG_DEST_ACCESS_KEY_ID=<AWS_ACCESS_KEY_ID> \
  -e RCLONE_CONFIG_DEST_SECRET_ACCESS_KEY=<AWS_SECRET_ACCESS_KEY> \
  -e RCLONE_CONFIG_DEST_ENDPOINT=<AWS_S3_ENDPOINT_URL> \
  rclone/rclone sync /source "dest:<AWS_STORAGE_BUCKET_NAME>/<AWS_MEDIA_PREFIX>"

# 3. Conferir contagem de arquivos nos dois lados antes de trocar o
#    STORAGE_BACKEND (mesma disciplina do CLAUDE.md global: nunca supor
#    que a cópia deu certo sem checar, é dado real de cliente)
docker run --rm -v uidcore_media_volume:/source alpine find /source -type f | wc -l

# 4. Só depois de confirmar: trocar STORAGE_BACKEND=local → s3 no
#    .env.prod (+ as 5 variáveis do bucket) e recriar o container backend
#    (docker compose -f docker-compose.prod.yml up -d --force-recreate backend)
#    — nunca só `restart` (não recarrega env_file, ver CLAUDE.md global)
```

⚠️ Qualquer novo `FileField`/`ImageField` adicionado em manutenção futura
(ex.: foto de perfil) já herda persistência e storage configurável
automaticamente — não precisa repetir este trabalho de infraestrutura,
só adicionar o campo no model.

## Padrões financeiros herdados do SystemD (aplicar desde o início, não só corrigir depois)

Regras completas e o porquê em `/home/notuidsoftware/.claude/CLAUDE.md`
(seção Módulo Financeiro — vale pra qualquer projeto Uid com livro caixa,
não só SystemD/UidCore). Resumo já adaptado pra nomenclatura do UidCore
(`is_active`, não `ativo` como no SystemD — `BaseModel` em `common/models.py`):

- **Cartão de crédito é uma `Conta` própria** (`tipo=CARTEIRA`, já existe em
  `TipoConta.choices`), nunca lançamento genérico direto no banco. Compra
  categorizada entra nela (Ferramentas, Impostos/IOF etc.). O pagamento da
  fatura no banco real TEM que creditar a conta do cartão — usar
  "Transferir entre contas" banco→cartão pelo valor pago, nunca só uma
  Despesa genérica marcada `is_active=False` no banco. `is_active=False`
  sozinho corrige o DRE mas deixa a conta do cartão sem saber que foi
  paga, inflando a "dívida" artificialmente (bug real encontrado e
  corrigido no SystemD em 29/07/2026 — 4 pagamentos históricos lançados
  assim deixaram o cartão R$400+ mais negativo do que a realidade).
- **CDB/aplicação rende sozinho** — a Conta de Aplicação/Garantia não
  fica parada no valor investido, o banco credita rendimento com o
  tempo. Conferir periodicamente o saldo bruto real no app do banco
  contra o saldo calculado no sistema; a diferença é rendimento não
  lançado — registrar como Receita (`tipo=RECEITA_FINANCEIRA`,
  `categoria=Investimento`, `is_active=True` — ENTRA no DRE, diferente
  de aporte/transferência) na própria Conta de Aplicação.
- **Fluxo de Caixa/Livro Caixa/Contas Bancárias vs Resultado (DRE) vs
  DFC** — três coisas diferentes: Fluxo de Caixa, Livro Caixa e saldo de
  Contas Bancárias TÊM que bater com o extrato real do banco sempre
  (incluindo transferência entre contas próprias e aplicação/resgate).
  Resultado do mês/DRE é operacional — soma só Receita/Despesa com
  `is_active=True`, nunca soma LivroCaixa bruto; aporte e transferência
  nunca entram aí. DFC (se vier a existir) é analítico, não precisa
  bater linha a linha com o banco.
- **Transferência entre bolsos do mesmo banco** (conta corrente ↔
  aplicação/CDB/conta remunerada, liquidez D+0/D+1) não é despesa nem
  receita — `is_active=False` na Despesa/Receita, mas o `LivroCaixa`
  continua mostrando o movimento real (não filtra por `is_active`, só por
  `estornado`).
- **Aporte ≠ Receita Financeira** — aporte de sócio é Patrimônio Líquido,
  nunca entra no DRE; rendimento de aplicação automática é Receita
  Financeira, separada da receita operacional.
- **Gasto em moeda estrangeira (USD) no cartão** — nunca recorrência fixa
  (`recorrente`/`frequencia`/`quantidade`). Câmbio varia mês a mês —
  lançar com o valor real da fatura quando ela chegar.
- **Estorno sempre em par** — `LivroCaixaViewSet`/`DespesaViewSet.estornar`
  têm que marcar `estornado=True` nos DOIS lados (lançamento original E o
  de reversão), senão duplica o efeito na soma em vez de neutralizar (bug
  real já corrigido tanto no SystemD quanto na Fase B do próprio UidCore —
  ver histórico de Manutenção #7 acima).

tipo` já tem `CARTEIRA`, `Despesa`/`Receita`/`Conta` já herdam `is_active`

## Complemento: cartão com garantia (CDB/aplicação) — cadeia de 3 contas

Refina o padrão de cartão de crédito documentado acima. Quando o cartão do
cliente tem limite por garantia (comum em cartão de banco digital tipo C6
Business — dinheiro aplicado em CDB destrava o limite), usar **3 `Conta`
encadeadas**, nunca só banco+cartão:

```
Banco (Conta Corrente)  →  Aplicação/Garantia (Conta Poupança)  →  Cartão (Carteira Digital)
```

Cada perna é uma **transferência entre contas** (endpoint dedicado, nunca
`Despesa`) — aplicar em CDB não é gasto nem sai do patrimônio do cliente,
é só troca de forma; usar o CDB pra quitar fatura é transferência
Aplicação→Cartão, não um pagamento novo. Sem a conta intermediária, o
dinheiro aplicado como garantia "some" do sistema — nenhuma tela mostra
quanto está garantindo o limite. Regra completa (e o porquê, com caso real
resolvido) em `/home/notuidsoftware/.claude/CLAUDE.md`, Módulo Financeiro.

**Cuidado técnico ao portar o endpoint de transferência pro UidCore:** se
a implementação calcular `saldo_anterior`/`saldo_atual` lendo o ÚLTIMO
lançamento por data (em vez de recalcular por soma agregada), qualquer
transferência com data retroativa deixa o saldo gravado temporariamente
errado — precisa de um comando tipo `reconstruir_saldo_livro_caixa`
(existe no SystemD) rodado depois de qualquer lançamento fora de ordem
cronológica. Vale conferir se esse mesmo padrão de cálculo foi copiado pro
UidCore e, se sim, portar o comando de reconstrução junto.
